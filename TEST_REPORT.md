## Исправление прав на мероприятия

После защиты обнаружен пропуск в сценариях: тестовая учётная запись имела отдельную роль организатора, а реальный профиль `tls` — модерку сайта без этой роли. Старый код разрешал публикацию только организаторам. Предыдущие успешные тесты не подтверждали создание мероприятия модератором.

Миграция 9 изменила единую функцию `campus_api.can_create_event`: публиковать могут организаторы **или модераторы всего сайта**. Локальная роль модератора/администратора сообщества не даёт доступа к общей афише. После снятия глобальной модерки право сразу исчезает, если отдельная роль организатора не назначена.

Проверка разрешения используется и при публикации, и для кнопки на обеих вкладках афиши. После создания из «Моих билетов» открывается список предстоящих событий с новой записью. Пустая афиша объясняет, кто может публиковать; модератору предлагается создать первое событие.

Новый серверный сценарий проверяет выдачу и снятие ролей, публикацию без роли организатора и выдачу билета участнику. Два новых браузерных сценария работают с действительно пустой тестовой афишей. Основной браузерный тест №18 теперь тоже входит под модератором без роли организатора.

На опубликованной версии `87a6d54` отдельный временный пользователь получил только модерку сайта; отсутствие роли организатора проверено непосредственно в Neon. Через интерфейс из «Моих билетов» он создал событие, затем другой участник получил бесплатный пропуск. После снятия модерки API сразу запретил новую публикацию. Право создавать мероприятия у существующего профиля владельца `tls` подтвердилось. Временные записи удалены. Результаты: [events-live.json](tests/reports/events-live.json).

## Удаление регистрации по коду

Осталась одна форма почты и пароля. Основной запрос — `POST /api/auth/register`; прежний `/register-domain` сохранён как совместимый адрес той же операции для уже открытых страниц. Маршрут `/api/auth/code`, экран подтверждения, повторная отправка, SMTP и Microsoft Graph удалены. Миграция 8 удаляет `email_codes` и пять устаревших функций и процедур, сохраняя пользовательские таблицы и сессии. Ранние SQL-миграции оставлены как история изменений.

Старые значения `AUTH_MODE=code` и `both` больше не включают письма и обрабатываются как `domain`. Адрес проверяется на окончание `@kbtu.kz`; владение почтовым ящиком не подтверждается.

После публикации версии `8c817525825d` проверена настоящая регистрация через интерфейс Render: форма не содержит поля кода, аккаунт создаётся и сразу входит, сессия переживает перезагрузку страницы, выход и повторный вход по паролю работают. Аккаунт найден непосредственно в Neon как регистрация по домену. Маршрут отправки кода возвращает 404 и отсутствует в OpenAPI. Миграция 8 применена, таблица кодов удалена. Временный проверочный аккаунт удалён. Результаты: [registration-live.json](tests/reports/registration-live.json).

## Исправление зависания при запуске

После сообщения пользователя о долгой надписи «Подключаемся…» устранено ожидание двух последовательных API-запросов перед показом формы. Публичные настройки входа теперь приходят в HTML; для гостя форма показывается без запроса сессии и обращения к БД. Наличие cookie служит только подсказкой о необходимости проверки: права по-прежнему проверяет API. HTML с этой подсказкой не кешируется.

Сетевые запросы ограничены 15 секундами, включая чтение JSON. При сбое проверки входа показана кнопка повторного подключения; cookie не удаляется. Если сам JavaScript не загрузился, независимый обработчик в HTML показывает кнопку перезагрузки при ошибке или после 12 секунд ожидания. CSS и небольшая программа темы включаются в HTML из тех же исходных файлов, поэтому не блокируют первое отображение отдельными сетевыми запросами. Модули интерфейса загружаются заранее, остальные статические файлы допускают кеширование с обязательной проверкой актуальности.

Пять браузерных регрессионных сценариев подтвердили это поведение. Два новых серверных теста проверили отсутствие доступа к БД для гостя и отказ в доступе при поддельной cookie. Заголовки `Server-Timing` и `X-App-Revision` позволяют различать время обработки в приложении и доставки ответа, а также проверять установленную версию.

### Найденный и исправленный сбой

До исправления при 50 пользователях 36 из 600 запросов получили ошибку 503; 95-й процентиль был 5 107 мс. Ожидающие соединение с PostgreSQL запросы занимали общие рабочие потоки FastAPI и мешали завершать запросы, уже получившие соединения.

В `server/db.py` ожидание соединений перенесено на отдельный ограничитель, а возврат соединения выполняется с защитой от отмены запроса. После изменения 50 и 100 пользователей прошли без ошибок. Первичные данные сохранены в `tests/reports/load-before.json`, повторный замер — в `tests/reports/load.json`.

## Как повторить

Инструкции и зависимости находятся в [tests/README.md](tests/README.md). Браузерный и нагрузочный прогоны выполняются последовательно: они очищают общую тестовую базу. Основная база приложения в этих прогонах не очищается.

Для демонстрации текущей версии корректная формулировка: «20 основных браузерных сценариев, 5 проверок запуска, 2 проверки пустой афиши и 12 серверных проверок прошли; в предыдущем локальном коротком прогоне 100 одновременных клиентов выполнили 1 200 запросов без ошибок. Предел облачного сервера требует отдельного измерения».
