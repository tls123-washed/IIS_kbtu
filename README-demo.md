# Campus Threads — исходное учебное демо

Этот разбор относится к отдельному демо в папке `site/`. Для серверной версии используйте [основное руководство](README.md).

Главное, что нужно понять сразу: **у этого приложения нет отдельного бэкенда**. Настоящая база данных PostgreSQL 18 запускается прямо в браузере пользователя. Ниже объясняется, как это работает, почему сделано так и как потом перейти на нормальный сервер.

---

## 1. Архитектура за одну минуту

```
┌──────────────────────── браузер ───────────────────────────┐
│                                                            │
│  index.html + styles.css      ← разметка и дизайн          │
│          │                                                 │
│  app.js  (экраны, кнопки)     ← «фронтенд»                 │
│          │  вызывает q(...) и tx(...)                      │
│  db.js   (слой запросов)      ← то, что обычно делает      │
│          │                       бэкенд: шлёт SQL в базу   │
│  PGlite  (PostgreSQL 18,      ← настоящая база, собранная  │
│          WebAssembly)            в WebAssembly             │
│          │                                                 │
│  IndexedDB                    ← файлы базы хранятся        │
│                                  в браузере                │
└────────────────────────────────────────────────────────────┘
```

Обычное веб-приложение устроено так: **браузер → HTTP → сервер (FastAPI) → SQL → PostgreSQL на сервере**.

Здесь средняя часть убрана: **браузер → SQL → PostgreSQL в браузере**. SQL-запросы при этом те же самые. Схема, триггеры и представления — это ваши файлы `01_schema.sql … 06_moderator_mentor.sql` без изменений.

### Почему так, а не FastAPI

| | Этот вариант (PGlite) | Классический (FastAPI + PostgreSQL) |
|---|---|---|
| Хостинг | статичный сайт, сервер не нужен | нужен сервер и база (Render, Neon) |
| Задача на защите | показать, что база работает | реальная соцсеть для многих людей |
| Данные | у каждого посетителя своя копия | одна общая база для всех |
| Безопасность | можно показать любой SQL, сломать нельзя | SQL спрятан за API, есть авторизация |

Для защиты по базам данных первый вариант удобнее: комиссия видит каждый запрос, может выполнить свой SQL и ничего не сломает другим. Для реального релиза нужен второй вариант (раздел 7).

## 3. Как запустить у себя

Нужен Python 3 (для сервера) и, если хотите запускать тест, Node.js 20+.

```bash
cd campus-threads-source
python serve.py             # или: npm run demo
# открыть http://localhost:8080
```

Почему нельзя просто открыть `index.html` двойным кликом: браузер запрещает загружать WebAssembly и модули со схемой `file://`. Поэтому нужен хоть какой-то HTTP-сервер — `serve.py` в 15 строк.

Автотест (в другом терминале, пока работает сервер):

```bash
npm install
npx playwright install chromium
npm run test:demo
```

## 4. Как это работает внутри

### 4.1. Запуск базы — `db.js → boot()`

```js
db = new PGlite('idb://campus-threads-kbtu');   // база хранится в IndexedDB
```

1. Создаётся PostgreSQL в браузере. Префикс `idb://` значит «сохранять файлы базы в IndexedDB», поэтому после перезагрузки данные остаются.
2. Если IndexedDB недоступна (например, в режиме инкогнито), база создаётся в памяти — это `catch` с `new PGlite()`.
3. Проверяем, есть ли уже таблица `moderators`. Если нет — по очереди скачиваем и выполняем `01 → 02 → 03 → 06.sql` через `db.exec(текст_файла)`. Это то же самое, что `\i 01_schema.sql` в psql.

Кнопка «Пересоздать БД» сначала запускает `00_demo_reset.sql`, затем загружает схему и учебные данные.

### 4.2. Каждый запрос попадает в журнал — `q()`

```js
export async function q(label, sql, params = [], conn = null) {
  const res = await (conn || state.db).query(sql, params);   // настоящий запрос
  push({ label, sql, params, ms, rows: res.rows.length });    // запись в журнал
  return res.rows;
}
```

Все экраны получают данные только через `q()`. Поэтому в панели «Журнал SQL» видно каждый запрос с параметрами, временем и числом строк — это и есть доказательство, что интерфейс работает через базу, а не через заранее подготовленные данные.

Параметры передаются как `$1, $2` — это защищает от SQL-инъекций так же, как в psycopg или SQLAlchemy.

### 4.3. Транзакции — `tx()`

```js
await tx('Публикация треда', async (t) => {
  INSERT INTO posts ...              // 1. сам пост
  INSERT INTO hashtags ... ON CONFLICT  // 2. хэштег: найти или создать
  INSERT INTO post_hashtags ...      // 3. связь M:N
});
```

Если любой шаг падает, PostgreSQL откатывает всё (`ROLLBACK`). В журнале видны `BEGIN` и `COMMIT`.

### 4.4. Что делает база сама, а не JavaScript

Здесь главная идея для защиты: часть логики живёт **в базе**, и приложение на неё опирается.

| Действие в приложении | Что делает PostgreSQL |
|---|---|
| Ответ в треде | триггер `trg_reply_community` сам подставляет `community_id` родителя |
| Регистрация | триггер `trg_students_subtype` не даёт сделать преподавателя студентом |
| Второй лайк | составной PRIMARY KEY `(user_id, post_id)` отклоняет дубль |
| Удаление поста | `ON DELETE CASCADE` удаляет ответы и лайки |
| Счётчик лайков | представление `v_post_details` считает `like_count` (производный атрибут) |
| Анонимный пост | `v_post_details` показывает «Аноним» вместо имени |
| Лента «Подписки» | функция `get_feed(user_id, limit)` из `03_views_triggers.sql` |
| Дерево ответов | рекурсивный CTE `WITH RECURSIVE` в `app.js` |

### 4.5. Вход по паролю

В `02_seed.sql` хранится не пароль, а bcrypt-хеш. При входе:

```js
SELECT ... password_hash FROM users WHERE username = $1   -- найти пользователя
bcrypt.compare(введённый_пароль, password_hash)            -- сравнить с хешем
```

При регистрации пароль сначала хешируется (`bcrypt.hash(пароль, 10)`), и в базу уходит только хеш. Пароль всех тестовых пользователей — `campus123`.

Честное ограничение: проверка пароля здесь идёт в браузере. Это нормально для демо, но в реальном приложении её делает сервер (иначе любой может открыть консоль и обойти вход).

### 4.6. Панель «Под капотом»

- **Журнал SQL** — список из `state.log`, который пополняет `q()`.
- **Таблицы** — читаются из системного каталога PostgreSQL (`information_schema.columns`, `pg_trigger`, `pg_views`, `pg_proc`, `pg_constraint`). То есть это не картинка, а живая структура базы.
- **SQL-консоль** — запросы берутся прямо из `sql/04_queries.sql`: берётся часть A, и файл делится по заголовкам вида `-- [1] Q1. …`. Можно написать свой запрос и `EXPLAIN ANALYZE`.
- **Ограничения** — 17 команд, каждая нарушает одно правило схемы. Каждая выполняется внутри транзакции, которую мы специально откатываем (`throw` внутри `db.transaction`), поэтому данные не меняются:

```js
await state.db.transaction(async (t) => {
  await q('Проверка', sql, [], t);   // если тут ошибка — правило сработало
  throw new Error('__passed__');      // если ошибки нет — всё равно откатываем
});
```

### 4.7. Экраны — `app.js`

Без React: каждый экран — это функция в объекте `VIEWS`, которая делает запросы и возвращает HTML-строку.

```
VIEWS.login / register / feed / thread / compose / profile / communities / community / search
```

- `go('thread', {id: 5})` — перейти на экран (история для кнопки «назад» хранится в `app.history`).
- Кнопки помечены `data-act="like"`, `data-act="follow"` …, и один общий обработчик клика вызывает нужную функцию из `ACTIONS`.
- Формы помечены `data-form="reply"` и т. д. и обрабатываются в `FORMS`.
- Весь текст из базы проходит через `esc()` перед вставкой в HTML — это защита от XSS (если кто-то напишет пост с `<script>`).

### 4.8. Дизайн — `styles.css`

- Фон цвета бумаги `#ecebe6`, тёмный текст, один акцент — синий `#1c3b7c` (для действий и хэштегов).
- Шрифты Onest (интерфейс) и JetBrains Mono (SQL) из Google Fonts.
- На компьютере «телефон» и тёмная панель БД стоят рядом. На экране уже 860px появляется переключатель «Приложение / База данных».

## 5. Как я это делал — по шагам

1. **Изучил материалы.** Ваш репозиторий `familyBudget` (Django + React — как образец структуры), файлы проекта: `ROADMAP.md`, SQL-файлы, EER-диаграмму, и две презентации-примера (RiSE App, Baspana).
2. **Проверил, что ваш SQL работает в PGlite.** Сначала запустил `01 → 02 → 03 → 06.sql` в Node.js через PGlite без браузера: всё выполнилось без изменений примерно за 2,5 секунды. Только после этого стало понятно, что идея «PostgreSQL в браузере» реальна.
3. **Написал слой базы** `db.js`: запуск, `q()`, `tx()`, журнал.
4. **Сделал экраны** в `app.js` по одному: вход → лента → тред → публикация → профиль → сообщества → поиск. Для каждого экрана сначала писал SQL, потом HTML.
5. **Добавил панель БД**: журнал, таблицы из каталога, консоль на основе `04_queries.sql`, проверки на основе `05_constraint_checks.sql`.
6. **Тестировал в браузере через Playwright**: скрипт сам входит, лайкает, отвечает, запускает проверки, делает скриншоты на компьютере и на телефоне (390px) и собирает ошибки из консоли. Исправил найденное: отступы в журнале SQL, растянутые аватары, шапку под «чёлкой» телефона, иконку сайта.
7. **Опубликовал**: сначала превью, потом проверка безопасности (ключей и секретов в коде нет, весь вывод экранируется), затем публикация на `kbtuthreads.pplx.app` и повторная проверка уже живого сайта в чистом браузере.

## 6. Как менять

- **Поменять схему или данные** — правьте файлы в `site/sql/`, затем нажмите «Пересоздать БД» в приложении (или очистите данные сайта в браузере).
- **Новый экран** — добавьте функцию в `VIEWS` в `app.js` и кнопку с `data-act="go" data-go="имя"`.
- **Новое действие** — добавьте функцию в `ACTIONS` и кнопку с `data-act="имя"`. Все запросы делайте через `q()`, чтобы они попадали в журнал.
- **Обновить библиотеки** — `npm install`, затем `npm run update-vendor`.

## 7. Следующий шаг: настоящий бэкенд (по ROADMAP)

Чтобы все пользователи видели одни и те же посты, PostgreSQL переезжает на сервер, а между браузером и базой появляется API.

```
React (Vercel)  →  HTTP/JSON  →  FastAPI (Render)  →  SQL  →  PostgreSQL (Neon)
```

Что переносится почти без изменений:

- **SQL-файлы** — выполняются один раз на Neon через `psql`.
- **Запросы из `app.js`** — каждый вызов `q(...)` становится эндпоинтом FastAPI. Например, лайк:

```python
@app.post("/posts/{post_id}/like")
async def like(post_id: int, user = Depends(current_user)):
    await db.execute(
        "INSERT INTO likes (user_id, post_id) VALUES ($1, $2)",
        user.id, post_id,
    )
```

- **Вход** — `bcrypt.checkpw` на сервере, после чего сервер выдаёт JWT-токен.
- **Экраны** — переписываются на React-компоненты, а дизайн и `styles.css` остаются.

Этот бэкенд можно сделать следующим этапом проекта, разбирая каждый шаг.
